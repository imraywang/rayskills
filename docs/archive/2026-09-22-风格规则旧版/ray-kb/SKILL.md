# Ray KB（口播生产与再分发）

用同一套口播能力承接两种真实起点：从灵感直接形成原生快速口播，或把已经核验的图文母稿改编成口播内容包。两种模式都只讲一个判断、守住事实边界，并在录制后学习 Ray 的实际表达；但快速模式不能被完整长文流程拖重。

## 固定原则

1. 长文再分发时，图文母稿是事实、判断和来源的唯一真源，衍生稿必须记录 `source_draft` 与 `source_sha256`。原生快速口播没有上游长文，口播稿本身是唯一活跃母稿，事实边界由本地知识、联网来源、个人观察及其核对记录共同约束；不能让文件指向自己，也不能自行增加事实、经历或效果数字。
2. 不写“亲测”“实测”或具体效果，除非当前模式的事实依据能证明用户真的做过。来源作者的实践保持归属，不改写成 Ray 的第一人称。
3. 一份口播稿只承载一个中心判断，只保留一个结尾动作。
4. 长文改编中发现母稿事实有问题时停下来交回 `ray-writer`，不在衍生口播里就地修事实。快速口播在“检索与事实边界”内解决事实缺口；如果需要大量调研、多个互相竞争的判断或完整图文论证，就退出快速模式，转入深度内容路线。
5. 不自动发布。未经用户明确要求，不生成图片卡片成品，不调用付费视频或图片生成。
6. 用户提供实际录制稿时，逐字稿以用户版本为准；生成稿保留为比较证据。录制完成不等于已经公开发布，平台、链接和时间未知时只标记 `recorded`。

## 选择工作模式

先按内容起点选择一种生产模式，不同时生成两套文件：

- **原生快速口播 `fast-oral`**：用户从灵感、现场观察、咨询案例或对话中的初步判断出发，没有一篇已经核验的完整长文。读取 [原生快速口播](references/fast-oral.md)，完成本地检索、必要的联网核对、唯一母稿、轻量录前检查和发布回流；不强制建立候选卡、写作任务、成稿包或第二份口播内容包。
- **长文再分发 `article-repurpose`**：输入是已经核验的完整长文，或能沿 `content-pack` 找到完整母稿。继续执行下方的长文输入门、角度选择、七段内容包和来源指纹检查。
- **审读或录后学习**：用户给的是现成口播稿、最终录制稿或 difference 请求，不重新进入生产模式，分别走本页后面的“四关审读”或“录后对照与学习”。

用户只说“做一条口播”、同时存在完整长文和新想法时，先判断本次事实是否要继承长文：继承就走长文再分发；新判断主要来自当前对话与新检索就走快速口播。无法一条讲清时，不把复杂内容硬塞进快速模式。

## 长文再分发输入门

只接收 `kind: draft`、`kind: article` 或已经发布的完整正文。收到 `content-pack`、调研或审核卡时，沿 frontmatter 的 `draft` 链接找到母稿；找不到就停止并说明缺口，不把任务说明当文章。

知识库根目录不写死：优先使用用户明确路径，再向上查找 `.ray-obsidian.json` 或兼容目录结构。找不到兼容知识库、用户只要一次性口播稿时，可在当前工作区交付对应模式的一份稿件，并说明这次没有进入知识回流；需要长期管线时先转交 `ray-obsidian`。

读取母稿、成稿包和事实清单，确认：

1. 哪些是已核对事实。
2. 哪些是来源作者的观点。
3. 哪些是 Ray 愿意署名承担的判断。
4. 哪些个人经历已被用户确认可以使用。
5. 哪些数字、产品状态和限制需要录制前再核对。

两种模式写新口播前都读取 [录后对照与表达学习](references/recording-feedback.md)：稳定规则全部检查，原型规则按当前叙事选用，待观察项不自动执行。学习推进方式，不复制某篇已录稿的表面句式。

## 先选视频角度

从母稿提取最多三个候选，每个候选写清：目标观众、一个中心判断、开场冲突、最强证据、能拍出来的画面，以及删掉后会失去什么。

选择标准按顺序执行：

1. 脱离工具名后，判断仍然成立。
2. 现有事实足以支撑，不需要编故事。
3. 前 8–10 秒能出现变化、矛盾或反直觉判断。
4. 中段有一个能被截图、录屏或真实操作证明的重心。
5. 结尾能给一个低摩擦动作。

用户未指定时长时，默认做 2–3 分钟、真人出镜加录屏或截图的混合口播。60–90 秒只保留一个反转和一个动作；5 分钟以上的教程必须把演示步骤与口播解释分层。

## 重写为口播

采用这条推进线：

```text
判断或冲突 → 观众熟悉的挫败 → 事实或真实演示 → 再判断 → 一个动作
```

写作时遵守：

- 第一句直接给判断、变化或冲突，不从背景和自我介绍开始。
- 一段只说一个动作；一句超过约 45 个汉字时优先拆开。
- 关键判断单独成句。连续三个术语时，插入人话解释、类比或画面。
- 口播只放观众必须听懂的内容。完整链接、命令、数字口径和补充步骤放在来源与说明栏。
- 画面必须证明一句口播，不能只做装饰。每个镜头标为 A-roll、录屏、截图、字卡或后续 B-roll。
- 只保留一个结尾动作。不要同时要求点赞、关注、评论、转发、进群和买课。

## 口播语气

- 像一个做过事情、愿意给出判断的人对朋友讲话：平视观众，不装导师，不念稿。
- 技术名词要落回真实动作、结果或代价；网感来自观众熟悉的场景和口语节奏，不靠热梗、感叹号和表情。
- 情绪来自主题的真实矛盾，可以用反问、停顿、短句和局部加速；不虚构愤怒、震惊、眼泪或现场对话。
- 删除署名后，观众仍能听出这是 Ray 的判断，而不是一段通用 AI 解说。

## 长文再分发输出文件

从长文改出的衍生稿与母稿一起放在 `<vault>/10-创作/30-文章草稿/`，文件名增加 `-口播稿`；以口播起稿、没有图文母稿的内容才放 `<vault>/10-创作/20-口播草稿/`，它自己就是母稿。衍生稿不是第二份母稿，frontmatter 至少包含：

```yaml
kind: oral-script
status: ready-to-record
source_draft: "[[母稿文件名]]"
source_sha256: "母稿完整文件的 sha256"
content_pack: "[[对应成稿包]]"
target_platform: "视频号 / 抖音 / B站"
target_duration_seconds: 150
video_format: "A-roll + 屏幕录制"
central_judgment: "观众看完只记住的一句话"
image_card_status: not-started
```

正文固定包含：

1. `## 选题卡`：观众、原有认知、中心判断、证据、主目标和唯一动作。
2. `## 三个开场`：反直觉、变化结果和具体场景各一个，明确最终采用项。
3. `## 逐字稿`：只放能直接念的文字，不混入括号提示、表格或镜头说明。
4. `## 拍摄节奏`：时间、口播关键词、画面、字幕重点和素材状态。
5. `## 素材清单`：已有、待录、待做、可删除四种状态。
6. `## 图片长文接口`：只记录视觉命题、建议页数和母稿来源，默认状态为 `not-started`。
7. `## 来源与录前核对`：原始链接、易变信息和录前检查项。

## 图片长文接口

本轮不把图片长文做成完整生产流程，只保留三个稳定输入：

- 一句话视觉命题。
- 6–10 页建议叙事顺序。
- 母稿路径、内容指纹与允许使用的图片来源。

后续建立独立视觉能力时，从这三个输入开始，不重新从长文猜判断，也不复制第三方公众号的可识别排版。

## 验证与交接

长文再分发完成后运行：

```bash
python3 scripts/oral_script_check.py <口播稿.md> --source <母稿.md>
```

原生快速口播运行同一个检查脚本，但不传 `--source`；脚本依据 `production_route: fast-oral` 自动使用轻量结构：

```bash
python3 scripts/oral_script_check.py <快速口播母稿.md>
```

检查失败就修改并重跑。脚本通过只证明相应模式的结构、来源边界和估算时长成立，仍要人工确认只有一个中心判断、结尾只有一个动作，并完整朗读一次；无法真实朗读时，必须明确时长只是字数估算，不能冒充录制时长已经实测。

需要做画面时，长文模式把口播稿路径、中心判断、拍摄节奏和素材清单交给 `ray-broll`；快速模式只交接唯一母稿与中心判断，由 `ray-broll` 按实际需要补画面。它不能反向修改事实和口播判断，真人出镜与录屏仍由拍摄计划承担。

## 口播稿审读

“审一下这篇口播稿”“哪里会让人划走”“能不能让人记住、转发”类请求走审读，不重新改编，按 `references/script-review.md` 执行：

1. 审前确认拍摄方式与目标观众；裸稿（没有母稿）只审传播设计，声明事实真伪不在范围内。
2. 按“停下 → 听下去 → 记住 → 传播”四关顺序输出状态表和分级问题清单（🔴🟡🟢），每条引用原文并给出能直接念的修法；深改时再过维特根斯坦透镜七问。
3. 诊断完主动问是否标记式改稿，用户不确认就不改；确认后只动呈现层——顺序、钩子、过渡、命名、画面化、结尾——不动事实、判断与数字。审读对事实不设岗：不核对、不质疑、不评论，修改数字或事实的请求指回母稿与 `ray-writer`，审读只负责把口播做好。
4. 审读不替代 `oral_script_check.py`：脚本管结构、时长和来源边界，四关管传播设计。长文再分发检查母稿指纹与七段结构；快速口播检查唯一母稿、事实依据和轻量结构。自产口播交付前两者都要通过。

## 录后对照与学习

用户给出最终录制稿、要求比较生成稿与实际表达，或要求把修改沉淀到以后写作时，按 `references/recording-feedback.md` 执行，不重新审稿：

1. 分别保留生成稿和实际录制稿的路径、版本或内容指纹；最终录制正文不再润色。
2. 母稿继续约束事实，实际录制稿约束字幕、归档和衍生表达。录制中出现的新数字原样记录，但在重新确认前不放大成封面或图文结论。
3. 先比较叙事发动机，再比较材料取舍、现实变化、口语桥和行动设计；不能只做逐句文字 diff。
4. 一次出现的变化只记为原型规则或待观察；至少两个独立录制样本重复出现，才升级为稳定规则。用户明确指定为长期偏好时除外。
5. 详细对照放回当前选题的调研目录，口播稿用 `recording_review` 链接该记录；不把个人样本直接堆进 `SKILL.md`。
6. 用户只要求对照和沉淀时，不再生成第三版，不改动已经录制的逐字稿，也不推断已经发布。

## 交付要求

长文再分发时，向用户交付母稿路径、口播内容包、估算时长和录前核对项，并简要说明选了哪个角度、放弃了哪些候选。快速口播时，只交付唯一母稿路径、中心判断、事实边界、估算时长和四关结论，不为交接再造一套文件。两种模式都要明确是否完成真实朗读，不把内部检查过程写成长报告。
