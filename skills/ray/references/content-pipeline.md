# Ray 长文生产管线

用于用户明确要求“把这个 idea 做成文章并送进公众号或 X 后台”“走完整条内容管线”或“把内容生产流水化”时。这里的“送进后台”固定指已验证草稿，不指公开发布。正常步骤连续执行；只有事实边界、核心判断、真人形象、登录或线上写入授权需要用户介入。

## 完成状态

以下条件同时满足才算完成：

- 本地长文通过事实、语气、情绪和移动端可浏览性检查。
- 用户要求口播分发时：口播稿只承载一个中心判断，母稿路径与内容指纹一致，逐字稿、拍摄节奏、素材清单和录前核对齐全，并通过口播检查。
- 公众号、普通 X 和所需的 X Article 封面按各自比例生成并实际查看。
- 用户要求公众号草稿时：本地富文本预览已确认；微信后台只更新原草稿或明确新建一份；回读的标题、摘要、封面、正文、署名和编码正确。
- 用户要求 X Article 时：X 后台只存在一份对应草稿，标题、正文、封面与本地版本一致。
- 所需平台的草稿状态、封面路径和内容指纹已回写。
- 未发布文章。

## 授权阶梯

进入平台阶段前，按用户当前这轮原话选择唯一一级。判定与 `ray` 主入口、`ray-wechat`、`ray-x-article` 用同一套，不在本文另作解释：

1. **`local_only`**：只生成 HTML、封面、交付包和本地预览，不碰任何线上后台。
2. **`draft_write`**：本轮原话同时出现具体平台和落点（“保存到微信草稿箱”“放进 X 后台”）时，允许线上写入并完整回读。
3. **公开发布**：不属于本管线。必须在草稿验收完成后另开任务，明确平台和具体文章；不能继承前文的“过稿”“推送”“进入下一阶段”或历史授权。

只指名平台、动词模糊的说法（“推送到 X”“推送到微信”“同步到两个平台”）不直接升为 `draft_write`：先把该平台的本地产物做完，再用一句话确认是否现在写进草稿箱，得到肯定答复才写。完全没指名平台落点的说法一律 `local_only`，不问也不写。

管线连续执行到平台阶段时，这一句确认是唯一需要用户介入的地方；确认一次覆盖本轮点名的平台，不覆盖另一个平台。公众号草稿授权不能用于 X，X 草稿授权也不能用于公众号。修复登录、白名单、出口 IP 或浏览器权限，只恢复原先已经授权的动作，不产生新的授权。不能确定时自动降到更安全的一级。

## 阶段与交接

### 0. `ray-obsidian`：准备本地内容地基（按需）

用户已有兼容知识库时跳过。没有知识库、但要求长期内容生产和知识回流时，先确定根目录，安全建立资料、知识、成稿包、调研、草稿、发布与素材结构。已有文件不得覆盖或移动；最终检查必须为 `ready`。

### 1. `ray-writer`：从材料到可读长文

输入：idea、剪藏、调研、已有草稿或用户真实经历。

必须交付：

- 正文、成稿包和事实清单。
- 一句话判断、核心冲突句、情绪曲线和传播句。
- 适合移动端浏览的结构：长文使用具体的二级标题作为阅读锚点；只加粗完整的关键判断；段落之间没有多余空行。

事实或作者经历不清时停在这一阶段；不能用流畅文字掩盖证据缺口。

正文主体是别人的文章时走译介模式，交付物换成译文和出处块，不建成稿包。授权是这条支线的第一道门：`source_permission` 只有 `granted` 和 `open-license` 能往下走到平台阶段，`pending` 把整条管线停在本地产物。联系原作者和开转载白名单都是用户动作，不代做。

### 2. `ray-cover`：从判断到平台封面

输入：完整正文、成稿包、一句话判断、核心冲突和传播句，不能只传标题。

必须交付：

- 一个清楚的编辑隐喻。
- 公众号、普通 X，以及需要时的 5:2 X Article 封面：默认 Image 2 一次生成画面与中文并逐字检查；出现错字、频繁改题或跨平台漂移时回退无字底图 + 确定性排版。
- 逐字正确、缩略图可读、标题没有被裁切的成品和清单。

各平台共享视觉母题，但不能拉伸同一张成品；兜底模式下图片模型不负责中文排版。

### 2A. `ray-writer`：从母稿到口播内容包（按需）

输入：通过检查的完整母稿、成稿包、事实清单、目标观众和期望时长。

必须交付：

- 最多三个口播角度，只选择一个中心判断进入成稿。
- 可直接念的逐字稿；镜头提示、来源和录前核对与逐字稿分离。
- 至少五个有效镜头的拍摄节奏，明确 A-roll、录屏、截图、字卡和可选 B-roll。
- `source_draft`、`source_sha256` 和 `image_card_status: not-started`，保证母稿仍是唯一真源。
- `oral_script_check.py` 通过；无法真实朗读时明确时长只是估算。

需要拼贴画面时把口播稿、中心判断、拍摄节奏和素材清单交给 `ray-broll`。真人出镜和录屏由拍摄计划负责；图片长文只保留视觉命题、建议页数与母稿来源，本轮不自动生产。

### 3. `ray-wechat`：从本地成稿到公众号草稿（按需）

输入：通过检查的 Markdown、公众号封面、署名策略和用户确认过的排版方向。

必须交付：

- 干净正文 HTML 和带复制按钮的手机端预览；没有空段落、英文拆词或署名占位。
- 用户确认后优先更新 frontmatter 中记录的原 media ID，没有 ID 且明确授权时才创建。
- 更新旧草稿时保留封面、作者和评论设置；写入后强制 UTF-8 回读。
- 核对标题、摘要、正文全部原文块、章节、重点、空段落和署名，再回写草稿状态。

排版预览确认与线上草稿写入是两道独立门。接口成功码不能代替回读验收；本 Skill 不发布文章。

使用固定出口解决 IP 白名单时，只改变请求路径，不改变动作级别。不得为了查重或验收调用 `freepublish/*`；草稿查重只读取草稿列表，写入仍走标准草稿流程并完成全文回读。

### 4. `ray-x-article`：从本地成稿到可恢复草稿（按需）

输入：通过检查的 Markdown、5:2 封面和交付包。

必须交付：

- 优先续写本地已记录的草稿 URL；没有 URL 才在 Drafts 按标题查重。
- 使用富文本粘贴保留二级标题和加粗，不把 Markdown 空行变成空白段落。
- 完成封面裁切确认、正文结构核对、Preview 检查和返回编辑页后的保存确认。
- 回写 `x_article_status: draft`、草稿 URL、封面路径、保存时间和内容指纹。

`Publish` 按钮及其确认弹窗不属于本阶段的操作对象；即使用户说“推送到 X”“走完整发布流程”，也只能交付并验证草稿。

## 恢复规则

| 状态 | 处理 |
|---|---|
| 正文已写入，封面因浏览器本地文件权限失败 | 保留同一草稿，回写 `draft-needs-cover`；权限开启后从原 URL 续传，不新建 |
| 草稿 URL 已存在 | 直接打开并核对标题；不可访问时才回 Drafts 查找 |
| 本地已是 `draft`，但用户提到过去上传失败 | 先核验后台当前状态；封面实际缺失才补传，不能按旧叙述覆盖 |
| 富文本粘贴失败 | 不接受带 Markdown 符号或多余空行的结果；恢复格式后重新核对数量 |
| 封面上传后出现 `Edit media` | 保持默认 5:2 构图，点击 `Apply`，再以封面显示和 `Remove photo` 为成功信号 |
| 保存状态没有更新 | 留在原草稿，等待可见保存状态；不能把“已经输入”当成“已经保存” |
| X 界面文字或结构变化 | 重新读取当前页面，以可见控件为准；不盲点坐标，不创建替代草稿 |
| 公众号文章已有 `wechat_draft_media_id` | 先读取并更新原草稿；不得调用新建接口制造重复项 |
| 公众号回读出现 `Ã`、`å` 等乱码 | 使用本地正确 HTML、frontmatter 标题和明确摘要覆盖同一草稿，强制 UTF-8 回读全文 |
| 公众号排版器自动加入署名或三连 | 按用户署名策略整块删除，重新生成预览和正文，再更新原草稿 |
| 公众号接口写入成功但正文数量不符 | 视为失败；比对全部原文块、章节、空段落和重点数量后原地修复 |
| 公众号 API 因 IP 白名单失败 | 在原草稿任务内修复固定出口；不改用发布接口，不跳过本地交付门和全文回读 |

## 最终验收

逐项核对：

1. 所需平台标题完全一致。
2. 正文首句、末句和全部原文块一致。
3. 空白段落为零；章节和重点数量与本地交付包一致。
4. 公众号封面 ID 保持正确；X 封面在编辑页和 Preview 都完整显示。
5. 公众号回读没有中文乱码，署名策略生效；X Preview 中作者、标题、段落和结尾正常。
6. 所需平台的最近保存状态可验证。
7. 本地草稿状态已更新为 `draft`，中断状态已清除。
8. 没有发布文章。
9. 用户要求口播时，口播稿的母稿指纹、估算时长、镜头数量和来源链接均通过检查。

## 发布之后：归档回流（不属于本管线）

公开发布是授权阶梯第 3 级，仍然不属于本管线，也不能由本管线触发——在平台上按下发布是用户动作。本节说的是发布**已经发生之后**怎么把结果记回知识库：这一步只写本地文件，不调用微信或 X 的任何接口，不打开浏览器。记录一件已完成的事不是发布。

`50-系统/40-自动化/发布归档/record_published.py` 承担其中可自动完成的部分，需要用户提供真实的公开地址和带时区的发布时间：

```
python3 record_published.py --article <正式稿路径> --platform x|wechat --url <公开地址> --published-at <带时区时间>
```

它写三处：正式稿的平台字段（`x_article_status` / `x_article_url` / `x_article_published_at`，或 `wechat_status` / `wechat_public_url` / `wechat_published_at`）、`40-发布/00-内容反馈/` 下的发布反馈卡（`due_at` 指向发布后 24 小时），以及顺着写作任务和审核卡找回的源头 X 书签（`processing_status: processed` 和指向正式稿的 `published_file`）。

它拒绝几类会让健康检查失明的写法：草稿编辑器地址 `https://x.com/compose/articles/edit/…` 不能当公开链接；没有时区的时间算不出 24 小时到期时间；同一篇稿子在同一平台已经记过另一个公开地址时报错停下，不覆盖。反馈卡只填空不覆盖，已完成的复盘不会被打回 `pending`。

剩下三步要人判断，脚本每次运行都会把还欠的列出来：把可复用观点写回 `20-知识/` 并更新 `knowledge_backfill_status`、标记已用角度并更新 `remaining_angles_status`、把候选选题改成 `partially-published` 或 `closed`。跑完这条命令不等于归档齐了。详细边界见该目录下的 `README.md`。
