# X Articles 浏览器能力契约

## 选择顺序

1. 当前宿主已经提供、且能复用用户登录态的浏览器控制 Skill 或工具。
2. 当前宿主提供的电脑控制能力，可以在用户可见的浏览器中点击、输入、上传文件和读取页面状态。
3. 都没有时，在进入编辑器前停止，说明缺少什么能力；不得用网页抓取、普通 X API 或新建无登录浏览器冒充完成。

宿主可能是 Claude Code、Codex、WorkBuddy 或其他兼容 Agent。不要在本 Skill 中写死某个宿主的工具名称；加载宿主对应的浏览器或电脑控制说明并遵守其截图、定位和用户接管规则。

## 最低能力

所选能力必须同时做到：

- 打开并保持 `x.com` 的现有登录状态。
- 读取页面可见文字和当前 URL。
- 通过可见控件点击 `Articles`、`Drafts`、`Write`、`Preview` 等入口。
- 向标题和富文本正文输入内容。
- 把本地 5:2 封面送进页面的 file input。
- 等待并确认保存状态。

缺少任意一项都不能承诺完整写入。若只能准备正文和封面，交付本地包并说明浏览器步骤尚未执行。

## 文件上传的真实形状

这一项和其他几项不一样，不要按"点按钮"去理解：

- **不要点 `Choose File`。** 点它会弹出系统原生文件对话框，那个窗口在浏览器控制能力之外，看不到也点不动，任务会卡死在那里。
- 正确做法是先用读页面／查找元素的动作拿到 file input 元素本身的引用，再用宿主提供的**专用文件上传动作**把绝对路径直接交给它。
- 这类上传动作通常带**路径白名单**：只接受用户已经共享给本次会话的文件（会话的输入输出目录、用户主动连接的文件夹）。知识库里的封面默认不在白名单内，这不是权限没开，是路径没共享。
- 通常还有单次总体积上限（Claude in Chrome 是 10MB）。5:2 封面正常都远低于这个数，超了就说明封面导出参数不对，回 `ray-cover` 修，不要在这里压缩。

宿主不同，动作名称不同，但这三条约束基本都在。进入上传步骤前先确认当前宿主具备"拿元素引用 + 直接送路径"这条链路；只能点按钮的能力不算具备上传能力。

## 操作纪律

- 每次交互前读取当前页面；界面变化后重新观察，不复用旧坐标。
- 优先按可见文字、角色和标签定位；坐标只用于同一张最新截图中的临时点击。
- 不通过注入脚本绕过文件权限、登录、发布确认或编辑器限制。
- 发布按钮始终保持未点击；不能为了观察确认弹窗点击第一个 `Publish`。本 Skill 固定只保存草稿，公开发布属于另一个任务。
