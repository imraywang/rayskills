# 译介与转载

原创管线默认"事实、经历和判断都属于 Ray"。译文和转载正好相反：内容是别人的，Ray 只承担翻译准确、引入理由和署名交代。所以它不能塞进原创流程，也不能因为"反正不是原创"就少走检查——它比原创文章多两道门：**授权**和**署名**。

## 两种形态

| `translation_mode` | 做什么 | 边界 |
|---|---|---|
| `full` | 全文翻译。保留原文全部论点和结构 | 不删改立场，不替原作者补论据。Ray 的话只能出现在译前引言和译后按语，并显式标注 |
| `digest` | 编译。只译其中一部分，并加入 Ray 的判断 | 逐段都要能分辨哪句是原文、哪句是 Ray。做不到就退回 `full` |

没有第三种。把原文论点改写成自己的话再署自己的名，不是编译，是洗稿；本 Skill 不做，也不因为"改写幅度够大"放行。

只想引用一小段、正文主体是自己的分析时，那是**带引用的原创文章**，走正常写作流程，不走这条支线。

## 授权门

这是硬门。`source_permission` 只有四个取值：

| 值 | 含义 | 能走到哪 |
|---|---|---|
| `granted` | 原作者或版权方明确许可（邮件、私信、平台白名单截图） | 可以进平台草稿 |
| `open-license` | 原文本身是 CC BY、CC BY-SA 等允许转载的许可，且译文按要求署名并注明许可 | 可以进平台草稿 |
| `pending` | 已联系但没回复，或还没联系 | 只能停在本地，不写任何后台 |
| `denied` | 明确拒绝 | 到此为止，不做本地成品 |

没有 `fair-use` 这一档。合理使用是法律判断，不由 Skill 代用户做出；说不清就是 `pending`。

**授权是用户动作**：联系原作者、确认许可协议、在公众号后台开转载白名单，都由用户完成。Skill 不代发邮件、不替用户判断"应该算可以"、不把沉默当默许。用户说已经拿到许可时，把凭据摘要写进 `source_permission_note`，写清是谁在什么时候通过什么渠道给的。

## Frontmatter

```yaml
kind: translation
translation_mode: full          # full 或 digest
title: "中文标题"
source_title: "原文标题"
source_author: "原作者署名"
source_url: "https://原文地址"
source_published: 2026-06-30    # 原文发表日期
source_language: en
source_permission: granted      # granted / open-license / pending / denied
source_permission_note: "作者邮件许可，2026-07-20；限非商业转载并保留链接"
translator: "Ray"
```

`kind` 用 `translation`（翻译）或 `repost`（原文即中文，整篇转载）。两者走同一套门。

## 署名块

frontmatter 只给机器看，读者看不到。**正文里必须有读者真的能看见的出处块**，放在正文最前或最后，至少包含原标题、原作者、原文链接、原文发表日期和译者：

```markdown
> 本文译自《原文标题》，作者 原作者署名，发表于 2026-06-30。
> 原文地址：https://原文地址
> 经作者许可翻译，译文由 Ray 负责，理解偏差以原文为准。
```

**链接写成纯文本，不写成 Markdown 超链接。** 公众号正文里的外链对多数账号点不开，URL 藏在 `href` 里等于读者拿不到出处；写成纯文本在两个平台都成立。用超链接时微信侧的交付门会降级为提醒，不拦，但读者那一头的问题没解决。

检查器按 `source_url` 和 `source_author` 是否出现在正文可见文字里判断。平台侧的 `prepare_article.py` 会再验一次——出处块被排版丢掉时，草稿写不进去。

## 不虚构原则在译文里怎么用

固定原则 1（缺素材不补故事）在这里更严，而且方向相反——不是"不许编"，是"不许改"：

- 原文没有的事实不能加，原文有的事实不能因为"中文读者不熟"就换掉。需要背景补充时写进按语，不塞进译文正文。
- **原文的第一人称永远是原作者的。** 不得改写成 Ray 的经历，也不得让读者以为是 Ray 做的。译文里的"我"只能是原作者；Ray 要用第一人称就写在按语里，并明确切换视角。这条是译介最容易出事的地方，检查器只能给提醒，最终由人逐处确认。
- 数据、日期和产品状态照译，同时标注原文发表日期。已经过期时在按语里说明，不在译文正文里偷偷更新成今天的数字。
- 术语不确定就保留原文括注，不猜。
- 原文的判断即使 Ray 不同意也照译；不同意写进按语，不在译文里替原作者软化或加强。

## 检查

```bash
python3 scripts/article_check.py <译文.md>
```

`kind: translation` 或 `repost` 时，检查器额外验证：授权字段齐全、`source_permission` 已放行、正文可见文字里有原文链接和原作者。译文长度按原文走，所以 `length-short` 降为提醒。

机械检查通过后仍要人工确认三件事：

1. 通读一遍中译，读起来是文章不是机翻。
2. 每一处"我"都确认过是谁在说话。
3. `digest` 模式下，原文与 Ray 的判断在版面上真的分得开。

## 平台交接

- `ray-cover`：封面照常生成。**不使用原文的配图或截图**，除非授权明确覆盖图片；隐喻可以来自原文的核心判断。
- `ray-wechat`：**不勾选原创声明**。公众号有正式的「转载」机制，需要原作者在后台把账号加进白名单，那是用户动作。译文进草稿箱后，是否声明转载、怎么声明，由用户在后台决定。
- `ray-x-article`：出处块必须随正文一起进编辑器，原文链接保持可点。
- 两个平台的 `prepare_article.py` 都会重新验一次授权和署名。`source_permission` 不是 `granted` 或 `open-license` 时，本地产物照做，后台一律不写。

## 落盘

- 译文进 `<vault>/10-创作/20-草稿/`，文件名用中文标题。
- 抓下来的原文备份进 `<vault>/30-资料/`，不进 `<vault>/20-知识/`——别人的观点不是 Ray 的长期知识。确实想沉淀时，另写一份自己的笔记并链接来源和译文。
- 成稿包不是必需的。译介没有"从材料装配判断"这一步；引入理由和按语要点直接写进译文 frontmatter 和按语。
