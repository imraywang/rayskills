# 原生快速口播

内容从灵感、现场观察、咨询案例或对话里的判断直接开始，没有现成长文时，用本模式。目标是缩短“想到”和“开机录制”之间的距离。

## 完成形态

整个生产阶段只保留一份文件：`<vault>/10-创作/25-口播草稿/<标题>.md`。它就是母稿，也是录制稿。

不要额外创建候选选题卡、写作任务、`content-pack` 或第二份口播包。用户本来就有相关笔记或调研，链接复用即可。

## 动笔前

1. 用一句话写出 `central_judgment`：这条视频只讲什么。
2. **核实立论点。** 找出中心判断依赖的那一两个事实（“这件事发生了”“这个数字是真的”“这东西没拍到”），先用一手来源查实。快速口播没有上游母稿，审读也不查事实，这一步是唯一的事实关口。查不实就换一个判断，或者把说法降到查得实、能说满的程度；不要带着没核实的立论点进正文，再把它丢进「待确认」。判断本身（“这一定会失败”）不用核实，照样说满。
3. 想清楚观众是谁、处境如何：这个判断和建议，放在中国大陆的现实里成不成立、做不做得到。不成立就换判断或换动作，不要靠加免责声明补救。
4. 按 [口播表达规则](voice.md) 读完样本。
5. 需要素材时，可以检索本地知识库、联网找新闻和数据。这些材料只是弹药，不是许可：立论点之外找不到证据的观点照样说，拿不准的地方进「待确认」。
6. 标题和开头钩子里的硬数字（涨了多少、几天、多少钱），能查到一手数据就先查（GitHub 星数用 OSS Insight 按天数据）。查出来和用户给的不一样，在对话里直接说出来并给替代标题，由用户定；正文照样说满。

一条视频讲不清、需要好几个章节才能展开的内容，建议用户改走长文。

## 观点型与叙事型

默认是**观点型**：Ray 下一个判断，用案例和经历撑住，结尾给观众明天做得出来的动作。

素材本身是一个故事（一次事件、一段现场、一组原始录音或影像），硬拧成人生建议会显得牵强时，走**叙事型**：

- 前大半段让故事自己推进，旁白负责把事实串起来，事实照实讲；
- 结尾换成 Ray 本人的一句判断，说满，可以不给行动建议；
- 素材里有当事人的原始录音、视频原声时，在正文里单独一行写 `【原声：原话或要点】`，标出原声插入的位置，原声前后的旁白要能接上。`【原声】` 行不算 Ray 念的字，不计入时长估算。

选了哪种写在 frontmatter 的 `script_shape: opinion | narrative`，不写就当观点型。

## 唯一母稿

使用知识库里的 `50-系统/30-模板/快速口播母稿.md`。frontmatter：

```yaml
kind: oral-script
status: draft
production_route: fast-oral
central_judgment: "观众看完只记住的一句话"
target_duration_seconds: 180
recording_status: pending
```

正文四段：

1. `口播正文`：只放能直接念的话，不混入镜头说明、列表或来源；唯一例外是叙事型里单独成行的 `【原声：……】`。
2. `待确认`：格式见 [口播表达规则](voice.md)，🔴 立论级最多一条。没有就写“无”。
3. `素材与来源`：用到的链接、本地笔记、截图或录屏想法。可以很短。
4. `录制与发布收尾`：状态、录后对照、发布确认、反馈和知识回写。

## 检查与录后学习

```bash
python3 scripts/oral_script_check.py <快速口播母稿.md>
```

脚本只查结构，不查风格：章节、列表和括号、🔴 条数、`【原声】` 行的格式。用户要求时再按 [口播稿四关审读](script-review.md) 审一遍。

用户给出实际录制稿时，按 [录后对照与表达学习](recording-feedback.md) 处理：保留生成稿版本，实际录制文本作为最终表达；录完只标记 `recorded`，不能推断已经发布。

## 发布回流

确认公开发布后，把最终逐字稿移到 `40-发布/50-口播视频/`，并完成：

- 确认实际发布平台；公开链接和准确发布时间可以留空；
- 建立正式反馈记录；
- 可复用的观点回写长期知识，或明确 `not-needed`；
- 有生成稿与录制稿差异时，留下对照入口。

`recorded`、已生成平台草稿和公开发布是三个不同状态，不互相推断。
